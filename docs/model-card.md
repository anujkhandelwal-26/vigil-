# Model Card — `setu-fusion` VIGIL fraud model v1.0.0

## Intended use
Real-time fraud risk scoring for digital-lending applications in the Indian market (consumer
durable, personal, two-wheeler, education top-up loans). Output feeds a **four-way policy**
(APPROVE / STEP_UP / REVIEW / DECLINE), not an automated accept/reject — every DECLINE and REVIEW
is reviewable by a human analyst, and every STEP_UP routes to additional verification rather than
rejection.

**Not intended for**: production underwriting without a live retrain against real applicant data,
any decision made without the audit trail and reason-code disclosure this system produces, or any
use that would rely on the protected attributes captured here (`gender`, `age`) as inputs — they
are excluded from the feature matrix by design.

## Training data
60,000 synthetic Indian digital-lending applications generated by `data/generator/generate.py`,
seed `20260921`, base rate 3.50%. See `README.md` "The dataset the model trains on" for the full
field dictionary and a representative record, and `dataset-audit.md` for why synthetic data was
chosen over three evaluated public benchmarks.

**Time-based split** (not random): 42,000 train / 9,000 calibration / 9,000 test rows, ordered by
`submitted_at`. A random split would let ring members (e.g. twelve `DEVICE_FARM` applications
sharing one device hash) land on both sides of the split, inflating reported performance — the same
risk we identified and rejected in the public benchmarks' random-split methodology.

## Model
- **Algorithm**: LightGBM (`LGBMClassifier`), isotonic-calibrated via `CalibratedClassifierCV`.
- **Regularisation** (deliberate): `max_depth=5`, `num_leaves=15`, `min_child_samples=60`,
  `subsample=0.7`, `colsample_bytree=0.7`, `reg_alpha=0.5`, `reg_lambda=2.0`. An unregularised
  LightGBM will happily memorise a designed synthetic signal to ~1.00 AUC — exactly the
  "too-good-to-be-true" pattern this project rejected in the public datasets (see
  `dataset-audit.md`). These settings keep the reported number closer to generalisable signal.
- **Class imbalance**: `scale_pos_weight` (≈28:1). No SMOTE — synthetic oversampling distorts the
  probability calibration the four-way threshold search depends on.

| Metric | Value |
|---|---|
| PR-AUC | 0.9962 |
| Recall @ 1% FPR | 1.0000 |
| Naive binary (threshold 0.5) decline rate | 3.48% |
| Naive binary FP rate | 0.02% |
| Four-way decline rate | 3.46% |
| Four-way FP rate | 0.01% |

### Why PR-AUC is reported instead of ROC-AUC alone
At a 3.5% base rate, ROC-AUC is misleadingly optimistic — a model can score well on ROC-AUC while
still producing a poor precision-recall tradeoff at operationally relevant thresholds. PR-AUC and
recall@1%FPR are what a fraud-ops team actually budgets against.

### An honest discussion of why PR-AUC is 0.9962, and why that's not the leakage we rejected elsewhere
A univariate check (documented in `dataset-audit.md`'s methodology, applied here too) shows **no
single feature exceeds 0.70 AUC** on its own. The near-ceiling PR-AUC comes from the model combining
~15 weakly-informative signals per typology into a compound rule the way a real fraud-ops team's
rule engine would — not from one feature encoding the answer. This is thematically intentional: the
model needs to be excellent on the five **known** typologies so that its failure on the sixth,
**held-out** `BOT_RING_NEW_VECTOR` typology (scores 0.18–0.24, all would-be APPROVE) reads as a
genuine blind spot rather than a sandbagged demo. The novelty channel below is what catches it.

## The unsupervised novelty channel
An `IsolationForest` (`n_estimators=200`, `contamination=0.02`) fitted on the behavioural feature
block of legitimate training rows. **Deliberately not blended into the calibrated risk score** —
blending would corrupt the probability the cost-based threshold search depends on. It is a parallel
signal (`anomaly_score` in every decision), surfaced as its own reason when it fires on a pattern
the supervised model has never seen.

## Explainability
SHAP `TreeExplainer` on the underlying LightGBM booster returns the top-5 contributing features per
decision, mapped through a static table (`app/features.py::FEATURE_TO_REASON_CODE`) to a
whitelisted, regulator-shaped reason code — framed as an **adverse-action reason code** under both
ECOA/Regulation B (US) and RBI fair-practice expectations, which require a lender to state the
specific principal reasons for a decline.

## Fairness
Post-hoc disparate-impact audit by gender and age band (computed on the test set, at the trained
thresholds), reported by `training/train.py`:

| Group | Approval rate | Disparate-impact ratio |
|---|---|---|
| Gender: F | 96.63% | 1.0000 |
| Gender: M | 96.40% | 0.9977 |
| Age ≤30 | 96.67% | 1.0000 |
| Age 31–45 | 96.43% | 0.9975 |
| Age 45+ | 96.12% | 0.9943 |

All ratios are well within the 80% rule. `gender` and `age` are read directly from the database for
this audit and are never passed to the model as features.

## Four-way action thresholds
Grid-searched to minimise expected cost (INR): `C_FN=₹150,000` (loss given a missed fraud),
`C_FP=₹8,000` (lifetime value of a wrongly hard-declined good customer), `C_STEPUP=₹150`,
`C_REVIEW=₹400`. Resulting thresholds: `t_low=0.05`, `t_high=0.75`, `t_decline=0.80`. See
`app/training/train.py::search_thresholds` for the exact vectorised search.

## Limitations
- Trained entirely on synthetic data — a production deployment requires retraining on real,
  consented applicant data before any live decisioning.
- The near-1.0 recall@1%FPR reflects the designed separability of the five known typologies, not a
  claim about real-world fraud detection performance.
- The novelty channel's contamination rate (2%) is a starting assumption, not calibrated against
  real base rates.
- `IsolationForest` and the calibrated LightGBM score are not compared for consistency beyond the
  demo's `BOT_RING_NEW_VECTOR` scenario.
